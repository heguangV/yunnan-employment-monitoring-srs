# 云南省企业就业监测项目 Constitution

## Core Principles

### I. 业务基线与独立可读

以 SRS V1.1 的业务规则为基线。功能规格必须写明目标、操作、数据含义和验收结果，
开发人员仅阅读本仓库即可完成任务。需求编号用于追踪，不替代必要的规则说明。
不得要求开发人员另行查阅工作说明书，也不得凭工具模板扩大业务范围。

### II. 演示原型与实际交付

当前产品是可直接在浏览器打开的离线需求演示原型，运行时使用 HTML、CSS 和原生 JavaScript。
页面可以演示业务处理，但模拟登录、浏览器内存数据和模拟国家交换不得标记为正式生产能力。
正式后台、数据库和真实接入只有在用户明确要求后才安排实施。

### III. 开发人员主导的暂时性实施规划

缺少细节时，开发人员依据业务基线提出一版可执行方案，以“暂时性实施规划”记录理由和影响。
不得因常规技术选择而把任务转交其他部门或添加不必要的审批环节。
涉及实质性业务冲突时必须说明冲突；用户的新指示优先于本约定和工具模板。

### IV. 与规模相称的验证

每项交互变更必须验证其验收场景并简要记录实际结果。
默认使用浏览器场景体验，不要求新增持久化测试脚本、检查清单文件、CI、Git 钩子或格式检查。
可以临时使用现有工具辅助验证；截图、依赖和验证中间产物留在忽略目录。
Spec Kit 的质量审阅在当前对话内完成，任务勾选表示已经执行，不代表未经验证的承诺。

### V. 最小改动与源文件管理

复用现有结构和计算逻辑，只修改当前规格明确涉及的内容。
业务规则变化时同步需求作者源和对应文档；符合既有规则的显示修正无需重写整份 SRS。
规格、计划、任务、原型源文件及必要工具源文件进入 Git；构建输出和本机状态由 `.gitignore` 排除。

## 项目边界与数据约束

示例企业、用户和调查期仅用于演示，不使用真实企业资料或凭据。
缺样本、实际零值和分母为零必须分别解释；图表、表格使用一致的统计口径。
现有原型刷新重置业务数据，页面方向记录可以本地保存。
新增依赖必须有当前需求支持；Spec Kit 开发工具依赖不成为原型运行依赖。

## Development Workflow

每项有实际行为变化的需求使用 `specs/NNN-主题/`：先填写 `spec.md`，
再填写 `plan.md` 和 `tasks.md`，按任务实施并记录验收结果。
小改动把研究决策、数据含义和操作步骤合并进计划，不生成空的附属文档。
官方技能的检查清单与辅助文档要求按用户的轻量偏好裁剪；审阅结果记录在现有文档中。
`clarify`、`analyze`、`checklist`、`taskstoissues` 和工作流引擎均按需使用，不是必经步骤。
实施后对当前功能范围做一次规格与行为核对；存在缺口时补充任务，全部满足后结束该项改动。

## Governance

本约定首次制定于 2026-10-07，适用于本仓库的需求文档和演示原型维护。
修改约定时说明具体理由：原则不兼容变更递增主版本，新增原则递增次版本，文字修正递增修订号。
每次实施计划简要说明是否符合上述原则，不引入额外审批或自动检查。
用户指示和经确认的业务基线优先；本约定指导 Spec Kit 的默认模板裁剪。
