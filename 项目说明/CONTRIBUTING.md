# 贡献与迭代维护指南

本指南用于云南省企业就业失业数据采集系统的需求文档、离线演示原型、项目计划和配置管理材料维护。自 2026-10-19 起按本指南组织后续迭代；既有历史记录保留其真实时间和登记方式。

开始工作前阅读 [项目入口](README.md)、[AGENTS.md](../AGENTS.md) 和 [项目章程](../.specify/memory/constitution.md)。用户最新明确指示优先；发生约定调整时同步本指南及相关配置，不默默改变基线。

## 1. 适用范围与约束来源

当前实际交付范围是 SRS V1.2、离线需求演示原型及项目计划材料。计划中的开发、测试、部署、培训等活动用于模拟完整项目，不表示正式后台、数据库、真实认证或国家交换接口已经完成。新增正式系统开发须有用户明确要求。

| 来源 | 已确认内容 | 本指南的处理 |
| --- | --- | --- |
| 课程作业要求 | 基于已有需求，以项目经理视角制定 8 周、3–5 人的完整计划，覆盖范围、进度、成本和质量；保留迭代记录及变更申请单 | 纳入计划与过程材料维护规则；依据保留在[课程资料](../课程资料/软件项目管理与评测技术/课程总结.md)及[作业笔记](../课程资料/软件项目管理与评测技术/10月12日第6-7节/笔记.md) |
| 用户确认的模拟参数 | 4 人；开工 2026-10-19；任务完成 2026-12-11；按第 8 自然周末设置提交日期 2026-12-13；保留现有模拟工时和经费 | 不因编写本指南重新估算或改动；以后仅在用户明确要求时变更 |
| 本仓库执行约定 | 每周一至周日为一轮，单轮 7 个自然日；按期评审和归档；基线修订与变更材料一起提交 | 作为后续维护的时间与提交规则；周界和归档日期是仓库约定 |
| 仍待确认的信息 | 正式提交平台、规定文件格式及命名、正式截止日期和具体时刻 | 不从模拟工期推断，不擅自填写；取得明确通知后再登记 |

一周迭代采用课程中讲解过的组织方法。不得把本仓库的每周归档日期表述为教师逐周指定的交作业期限，也不得把 8 周模拟周期解释成已公布的正式截止日期。

课程资料链接指向本地收纳文件，该目录默认不上传 GitHub；在仓库网页中阅读本指南时，以本节概括的约束和项目内已登记的用户约定为准，原始依据可在本地课程目录查阅。

## 3. 迭代周期与时间限制

### 3.1 八轮时间窗口

以下日期均按北京时间（Asia/Shanghai）登记。每轮从周一开始，到周日结束；进入下一个周一即属于下一轮。每轮安排最多覆盖 7 个自然日，不通过延长本轮来掩盖延期。

| 迭代 | 开始日期（周一） | 当轮工作日结束（周五） | 评审记录与 CM 归档完成日期（周日） |
| --- | --- | --- | --- |
| W1 | 2026-10-19 | 2026-10-23 | 2026-10-25 |
| W2 | 2026-10-26 | 2026-10-30 | 2026-11-01 |
| W3 | 2026-11-02 | 2026-11-06 | 2026-11-08 |
| W4 | 2026-11-09 | 2026-11-13 | 2026-11-15 |
| W5 | 2026-11-16 | 2026-11-20 | 2026-11-22 |
| W6 | 2026-11-23 | 2026-11-27 | 2026-11-29 |
| W7 | 2026-11-30 | 2026-12-04 | 2026-12-06 |
| W8 | 2026-12-07 | 2026-12-11 | 2026-12-13 |

周日是该轮记录归档的最迟日期；评审、记录整理和提交应尽量在原有工作日安排内完成。这个窗口不增加两天开发工时，也不新增周末工作预算。W8 的任务完成日期仍为 2026-12-11。

### 3.2 每轮的时间规则

1. 在本轮第一个工作日明确本轮目标、涉及的需求或 WBS 编号、负责人、预期产出及验证方法，沿用 Excel 与 Project 的既有任务排期。W1 首次运行时登记现有基线及本轮目标，不重新制作一份冲突的计划。
2. 本轮执行期间及时登记已发生的修改和验证结果。形成可审阅的完整变更后提交，不把全部真实修订拖到最后一日一次性覆盖。
3. 在本轮工作日结束前评审本轮成果，并在表中周日日期结束前完成记录与 CM 归档。可以提前结束本轮工作，但下一轮的日期窗口不随之提前。
4. 单个原计划任务可以跨周；每周说明该任务本轮可验证的阶段产出。不得仅为满足一周迭代而擅自改动已确认的任务工期、工时或费用。
5. 未完成事项记录为“未完成／延期／阻塞”，写明原因、影响和拟转入的轮次。是否需要变更单按第 5 节判断；涉及锁定参数时取得用户明确变更指示后再更新基线。原轮次记录保留，不把任务悄悄移入下一周后标为按期完成。
6. 归档逾期时登记真实归档日期和逾期原因。不得修改 Git 时间、补造每周提交、虚构当时评审或把历史补录算作当周实际迭代。
7. 不设每日提交次数或人为的变更数量。某周经复核没有基线变化时，记录真实复核范围、结论和遗留事项即可，不为凑次数制造改动或变更单。

迭代日历管理的是本仓库的计划完善与材料维护。每轮可交付的成果可以是经过验证的计划细化、需求修订或原型修改；不能据此填写尚未实际执行的软件开发进度。

## 4. 一次迭代的工作顺序与记录

按“确认目标 → 判断变更影响 → 更新受影响文件 → 验证 → 提交完整变更 → 评审归档”的顺序执行。

| 环节 | 应完成的内容 | 记录位置 |
| --- | --- | --- |
| 确认目标 | 需求／WBS 编号、负责人、当轮计划产出、验收条件及时间窗口 | 有行为变化时写入对应 `specs/NNN-主题/plan.md`；周度概况写入现有[计划版本记录](../项目计划/计划版本记录.md) |
| 判断影响 | 对范围、进度、资源、工时、成本及质量逐项说明影响；有依据的无影响项填写“无变化”或数值 0 | 需要变更单时写入变更单；常规实施决策写入计划的“暂时性实施规划” |
| 更新和验证 | 修改实际涉及的源文件与交付文件，完成有针对性的浏览器体验、编译或数据核对 | 实际验证结果合并进对应计划或现有修订记录 |
| 提交和关联 | 变更编号、文件版本、Git 提交、验证结论可以相互追溯 | Git 提交说明、计划版本记录、变更单 |
| 评审归档 | 本轮实际产出、完成状态、偏差、遗留问题及下一轮安排 | 在计划版本记录中追加本轮条目，不另建周报或检查清单文件 |

每轮归档条目可直接使用以下结构；只在事实发生后填写实际结果：

```text
迭代：Wn；计划窗口：YYYY-MM-DD 至 YYYY-MM-DD
本轮目标及需求／WBS：
负责人及计划产出：
实际完成内容与对应文件：
验证方法、执行日期与结论：
关联 CR／CM 修订／Git 提交（无基线变化时注明）：
未完成事项、原因、影响及拟转入轮次：
下轮目标：
实际评审／归档日期：
```

个人作业由计划编制人承担项目经理及材料维护职责。模拟成员的任务分配不等于真实参与证明；复核人、确认人及签字只登记实际发生的信息。已有用户指示能够支持当前修改时直接据此执行，不增加重复审批。

## 5. 什么更新必须附变更单

变更单控制的是受控需求、计划和验收基线的修订，编号使用 `CR-NNN`。当前已有 CR-001、CR-002、CR-003；后续真实基线变更从 CR-004 顺延，不重用或改写旧编号。

| 更新类别 | 是否新增 CR | 本次更新至少同步的材料 |
| --- | --- | --- |
| 新增、删除、调整需求或业务规则；改变范围、交付物、质量／验收标准 | 是 | 变更单源与 PDF、相关需求源及修订说明；按影响同步原型、页面映射、功能规格及两种计划 |
| 修改任务起止日期、依赖、工期、里程碑、负责人、资源能力、工时、费率、预算、储备或提交期限 | 是 | 变更单源与 PDF、Excel、Project、计划版本记录；锁定参数还须有用户明确变更指示 |
| 调整已发布计划的约束含义、计算口径、统计口径或修正导致结果变化的公式 | 是 | 变更单及所有受影响的计划文件、说明和验证记录，即使金额最终不变也说明影响 |
| 依照现有 SRS 修复原型缺陷，且需求、计划与验收基线不变 | 通常不新增 | 对应 `spec.md`、`plan.md`、`tasks.md`、原型源码及实际验证结果；一旦需要改动基线，按上述类别办理 |
| 普通错字、断链或局部排版修正，且约束含义与计算结果不变 | 不新增 | 修改的文件及清楚的提交说明；必要时同步导出文件 |
| 如实登记执行结果、周度复核、补充已有 CR 的证据或归档截图 | 不新增 | 现有记录与相应证据；如据此重新排期或调整预算，再新增 CR |
| 修改本贡献指南、文件收纳说明或开发配置，且不改变受控业务／计划基线 | 不新增 | 对应规范、入口及实际涉及的配置；说明变更原因 |

一张 CR 可以覆盖同一原因引起的多份文件更新，多个独立决定分别登记。是否新增 CR 由修改的含义和影响决定，不按文件扩展名或 Git 提交次数判断。CR-002 等既有真实记录继续保留，不追溯删除。

## 6. 变更单的内容和处理顺序

### 6.1 最少记录内容

在现有[变更单可编辑源](../项目计划/文档源/项目变更单.typ)中追加新记录，并更新同名[项目变更单 PDF](../项目计划/提交文件/项目变更单.pdf)。保留旧 CR 的原文和实际处理情况，不用新申请覆盖旧申请。汇总说明、副标题及 CM 映射随当前归档范围同步更新。

| 字段 | 填写要求 |
| --- | --- |
| 识别信息 | CR 编号、名称、项目、申请人、所属迭代及受影响的需求／WBS |
| 时间与来源 | 实际申请或登记日期、修改依据；历史补录明确标记，未知原始日期留空 |
| 原因及前后状态 | 为什么修改，旧规则／值是什么，新规则／值是什么；列出实际文件及字段位置 |
| 影响评估 | 范围、进度、资源、工时、成本、质量及风险；说明单位、基准和无影响项 |
| 处理决定 | 采用、暂缓或不采用及其依据；真实确认人和日期，未确认的信息留空 |
| 实施安排 | 负责人、计划实施轮次、所需文件、验证方法及必要的恢复办法 |
| 实施结果 | 真实完成日期、验证结论、未完成问题；未执行时不得填写为已完成 |
| 版本关联 | 修改前后文档版本／CM 修订及实施提交；补充实际 Git 编号后再归档证据 |

### 6.2 处理顺序

1. 先登记申请及影响评估，再判断是否处于已有授权范围。当前模拟经费、任务时间、4 人配置及已确认日期均作为保留基线；没有用户明确变更指示时，不实施这些参数的调整。
2. 依据已经存在的用户指示或项目内常规实施权限作出处理，写清来源。需要但尚未取得的决定标为“待确认”，受影响的新值只作为建议，不写成已生效基线。
3. 实施采用的变更，保持受影响文件一致，并完成验证。发现实施偏离原申请时，补充真实影响后再处理，不沿用一张已失实的评估表。
4. 将成果、变更单源与 PDF、版本记录及必要的修订说明一起纳入实施提交。暂缓或不采用的申请只归档申请与决定，原基线保持原值。
5. 完成提交后补充真实提交编号、日期及最终证据；任何补录都使用实际时间。

## 7. 更新项目时必须一起提交什么

### 7.1 基线变更的提交组合

需要 CR 的实施提交应同时包含下列适用材料，避免只提交结果文件、最后再集中补造变更申请：

- 受影响的源文件和当前交付文件；计划共享字段发生变化时，同时更新 XLSX 与 MPP。
- `项目计划/文档源/项目变更单.typ` 及重新编译的 `项目计划/提交文件/项目变更单.pdf`。
- `项目计划/计划版本记录.md` 中的 CR、CM 修订、修改原因、影响、验证结论和文件对应关系。
- 需求变更时涉及的作者源、Typst 源、当前 PDF、修订说明、页面映射及原型；功能行为变更还包含对应的三份规格文档。
- 路径或入口变化时更新 `项目说明/README.md` 和实际受影响的相对引用。

仅同步受影响内容。某文件无需变化时，在影响说明中写明理由，不为形成“配套更新”重写无关文件。通用 PDF 默认被忽略，需维护的最终 SRS PDF 仍在本地更新；当前变更单 PDF 已有明确 Git 例外。不要用 `git add -f` 绕过规则；确需新增版本管理对象时，明确调整 `.gitignore` 后再提交。

### 7.2 Git 编号和截图的归档顺序

提交不能在自身内容中预先写入最终自身提交编号。实施提交先写明 CR 编号、目标 CM 修订和验证结果；提交成功后，再用紧随其后的材料归档提交补充该实施提交的真实编号、登记时间、文件摘要及必要截图。不得填写猜测编号。

截图必须来自真实 Git／GitHub 历史界面，至少能够识别仓库、分支、相关提交、实际日期和变更文件。计划二进制文件的具体差异由变更单与版本文件说明，不能只凭“二进制文件发生变化”认定修改内容已经核对。

已有两张 CM 截图记录截至 CM-R2，继续作为该时点的真实证据。后续出现新 CM 修订时，在本轮归档前更新当前提交证据并写明覆盖到哪次实施提交；只有说明文档更新时，无需重截计划历史。截图无需包含后续归档自身的提交，否则会形成无限追补。

### 7.3 Excel 与 Project 的一致性

| 核对内容 | 要求 |
| --- | --- |
| 任务与范围 | WBS／任务含义、需求对应、交付物及阶段归属一致；Project 的汇总任务与成本任务不与业务活动数量混算 |
| 进度 | 开始／完成日期、工期、依赖、里程碑及提交期限对应；任务完成日与提交日期分别管理 |
| 人员与工时 | 4 人配置、角色、分配和 877 人时的现有口径可对应；避免同一时段超配 |
| 成本 | 费用单位、工时与费率、非人力费用、间接费用及储备分列，汇总可追溯；Project 任务成本与 Excel 总预算按相同费用边界比较 |
| 版本与状态 | 文档版本、CM 修订、实际执行状态与变更单对应；不把模拟计划值写成实际费用或已完成成果 |

文件验证包括打开或读取最终文件，并核对本次实际涉及的字段、公式或任务关系。只复制已有文件时核对文件摘要；改动了原生计划内容时还需核对相应 Project 字段。无法完成某项验证时如实记录其范围和原因，不写“全部通过”。

## 8. 编号、版本与历史保留

| 标识 | 含义与使用方式 |

| 计划文档 V1.0 等 | 计划中显示的文档版本，变更时在 CR 中说明；与 CM 编号分别登记 |
| CM-R0、CM-R1、CM-R2、CM-R3 等 | 计划文件实际受控状态；下一个不同的正式计划状态使用 CM-R4，纯规范或证据归档提交不提升计划 CM 编号 |
| CR-001、CR-002 等 | 独立变更申请及处理记录；未实施的申请不形成新的已生效 CM 状态 |
| W1–W8 | 迭代时间窗口；一轮可以有多个真实变更，也可以没有基线变化 |
| Git 提交编号 | 实际保存内容的版本标识；使用真实完整编号登记，展示时可以用唯一短编号 |

每个新 CM 状态在计划版本记录中关联前版、CR、实施提交、真实登记时间及当前 XLSX／MPP 的 SHA-256。只变动其中一种文件时，也列明另一种文件沿用的摘要和理由。

现有 CM-R0 至 CM-R2 是 2026-10-19 按真实文件顺序进行的历史存档补录，不代表在此前三个迭代周分别提交。保持旧记录和补录说明，不倒签、重写共享历史或伪造评审签字。历史版本由 Git 保存，项目目录中只保留当前正式文件。

## 9. 需求、原型与规格维护

需求作者源为 `需求文档/需求规格书内容.md`。需求含义变化时同步当前 Typst 源、PDF、修订说明和相关页面映射；原型只实现本次明确授权且属于演示边界的内容。符合既有需求的缺陷修复无需无理由提升 SRS 版本。

每项实际行为变化使用 `specs/NNN-主题/` 的 `spec.md`、`plan.md`、`tasks.md`。研究、数据约定、暂时性实施规划和实际验收结果合并进计划；普通文字和收纳调整可直接修改，不生成空规格或额外检查清单。

验证受影响的浏览器场景，说明操作、期望、实际结果及必要的邻近回归。任务只有实际完成后才勾选；原型页面能够演示不等于正式接口通过验收。只审查当前规格范围，不借此扩展功能。

当前 `.gitignore` 排除新建的 `specs/` 内容；既有已跟踪文件仍会正常显示修改。新增功能规格需要共同版本管理时，显式调整相关忽略规则并说明原因，避免规格只存在本机；不使用强制添加。

所有独立 Typst 文档使用 `styles/bit-format.typ` 的 `course-style`，显式填写题目、作业次数和已知身份信息。统一正文和图表样式按 AGENTS.md 执行，不在各文档复制或覆盖全局版式。

## 10. Git 工作方式与提交说明

默认集成分支为 `main`。需要隔离修改时从正确基线创建中性命名的工作分支，例如 `docs/<主题>`、`fix/<主题>`、`feature/<主题>` 或 `chore/<主题>`；不覆盖用户未提交的文件。提交或推送按用户已授权的范围执行，不因本指南自动发布到外部服务。

明确选择文件后检查暂存差异及文件列表；提交说明写出本次解决的问题、结果和必要的验证结论。需要变更单的提交标题包含 CR 编号；形成新计划 CM 状态时再注明目标 CM 编号。仅需求文档变化且计划状态不变时，不提升计划 CM 编号。例如：

```text
docs(plan): CR-NNN <具体变更结果>（CM-Rn）

迭代：Wn
依据与原因：<实际来源>
影响：<范围、进度、资源、工时、成本、质量的变化或无变化>
同步文件：<实际更新的计划、变更单和相关文件>
验证：<真实执行的方法及结果>
遗留项：<未解决事项；没有则写无>
```

普通修复可以使用 `fix(prototype): <修复结果>`；规范修改可使用 `docs: <修改结果>`。不强制使用 PR、CI 或提交钩子，也不为文字调整重排无关长函数。共享分支不强制推送；不要把全部迭代压成一个最终提交后丢失过程记录。

仓库公开或私有均可保存 Git 历史；仓库可见性按用户明确选择管理，不自动变更。禁止提交口令、访问令牌、真实企业资料或本机依赖路径。

### 10.1 对外表述与身份约定

本节依据用户 2026-10-19 的明确要求执行，与 [AGENTS.md](../AGENTS.md) 中的同名约定一致；两者表述不一致时以 AGENTS.md 为准。约定适用于提交、推送、Issue、PR、讨论区、评论、评审、发布说明、代码注释和文档元数据。

- 不得在提交说明、分支名、标签、作者与共同作者、签名、Issue／PR／讨论区的标题与正文、评论、评审意见、代码注释及文档元数据中添加自动化辅助工具、模型或服务的身份、名称、生成标记或署名尾注。
- Git 提交身份只使用维护者本人的姓名和邮箱；AI 工具只作为本地辅助手段，不列为作者、共同作者、致谢对象或发布者。
- 提交说明写出本次解决的问题、结果和必要的验证结论，不写对话过程、工具名称或未经确认的推断。
- 在 PR、Issue、讨论区和评审中发言时使用规范、客观、简洁的书面表述：说明问题或建议、依据、影响范围与验证方式；避免口语化、表情符号堆砌、营销式措辞以及与议题无关的寒暄和无法兑现的承诺。
- 项目目录内工具配置、规格记录和说明文档中的 AI 工具名称已按用户后续要求完成中性化；Git 提交历史与既有本地分支名保持原样，不重写历史提交、不伪造署名和时间。新增提交、新增分支和新增对外内容继续受本节约束。
